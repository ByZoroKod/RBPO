# Аукцион коллекционных предметов: JWT access/refresh

Это REST API для аукциона. Пользователь выставляет свой коллекционный предмет на торги, другие делают ставки,
а когда торги заканчиваются, победитель получает предмет. Написано на Java 17 и Spring Boot, данные хранятся
в MySQL.

В этом задании вход по HTTP Basic заменён на JWT: после входа или регистрации выдаётся пара access и refresh,
а каждая выданная пара записывается в таблицу `user_sessions`. Роли, права и бизнес-операции остались такими же,
как в прошлом задании.

## Endpoint'ы аутентификации

| Endpoint | Тело запроса | Успех |
|---|---|---|
| `POST /auth/login` | `username`, `password`, `deviceId` (необязательно) | `200` |
| `POST /auth/register` | `username`, `password`, `name`, `email`, `deviceId` | `201` |
| `POST /auth/refresh` | `refreshToken` | `200` |

Ответ всех трёх: `{"accessToken": "...", "refreshToken": "..."}`. Access передаётся в заголовке
`Authorization: Bearer <access>`, refresh только в теле `/auth/refresh`. Для `/auth/refresh` access и пароль
не нужны.

## Токены

- Оба токена JWT с подписью HS256. Секрет лежит в `.env` (`JWT_SECRET`, Base64, не меньше 32 байт).
- В каждом токене есть `sub` (логин), `jti` (новый для каждой выдачи), `type` (`access` или `refresh`),
  `iat` и `exp`. Срок жизни задаётся в `application.yml`: access 15 минут, refresh 7 дней.
- `JwtService` создаёт и проверяет access и refresh отдельными методами. Проверка смотрит подпись, срок,
  обязательные claims и `type`. Фильтр `JwtAuthenticationFilter` принимает только access, `/auth/refresh` только
  refresh.
- При каждом запросе фильтр берёт пользователя из базы, поэтому заблокированный пользователь сразу теряет доступ.
- CSRF отключён: токен передаётся в заголовке, а не в cookie, поэтому браузер не подставит его в чужой запрос.

## Сессии

Таблица `user_sessions` (сущность `UserSession`): `id` (UUID), `username`, `device_id`, `refresh_token` (TEXT,
уникальный), `access_token_expiry`, `refresh_token_expiry`, `status`. Статусы `SessionStatus`:

- `ACTIVE`: refresh ещё не использован;
- `USED`: refresh обменян на новую пару;
- `REVOKED`: refresh отозван.

Одна строка соответствует одной паре. Сроки в строке равны `exp` токенов с точностью до секунды.
В MySQL на столбец TEXT нельзя напрямую поставить UNIQUE, поэтому уникальность обеспечивает индекс по
вычисляемому столбцу `refresh_token_hash` (SHA-256 от токена). По нему же идёт поиск сессии.

Обмен refresh (`TokenService.refresh`) выполняется в одной транзакции:

1. Проверить refresh как JWT с `type = refresh`.
2. Найти сессию и заблокировать строку (`SELECT ... FOR UPDATE`): из двух одновременных запросов с одним
   refresh второй ждёт первого и получает отказ.
3. Проверить, что пользователь существует и активен, `sub` совпадает с владельцем, статус `ACTIVE` и срок
   не истёк.
4. Старую сессию перевести в `USED`, создать новую пару и новую строку `ACTIVE` с тем же `deviceId`.

Если новую пару сохранить не удалось, вся транзакция откатывается, и старая сессия остаётся `ACTIVE`.
Если пришёл ещё не истёкший refresh со статусом `USED`, сессия переводится в `REVOKED` и возвращается `401`.
Это изменение сохраняется (`noRollbackFor`), хотя ответ ошибочный.

Регистрация и сохранение сессии тоже в одной транзакции: если сессия не сохранилась, пользователь не создаётся.
Проверки регистрации остались прежними: логин 3–50 символов и уникальный, пароль не короче 8 символов
с заглавной, строчной буквой и цифрой, роль всегда `USER`.

## Ошибки

| Код | Когда |
|---|---|
| `400` | нет обязательного поля или оно пустое, слабый пароль, сломанный JSON |
| `401` | неверный логин или пароль; нет access или он неверный, просрочен, не того типа; refresh неверный, просрочен, не того типа; сессия неизвестна, использована или отозвана |
| `403` | роль не позволяет выполнить операцию |
| `404` | не найдено |
| `409` | логин занят, нарушено правило бизнеса |

Ответ об ошибке: `status`, `message`, `timestamp`, токенов в нём нет. После 5 неверных паролей подряд вход для
этого логина закрывается на 15 минут.

## Роли и права

Ролей две: `USER` (участник торгов) и `ADMIN` (модератор). Обычный пользователь видит и меняет только своё:
профиль, предметы, свои торги и сделки. Ставки делает только `USER`, от своего имени. Администратор управляет
пользователями и может напрямую создавать, менять и удалять лоты, ставки и сделки. Правила по адресам описаны
в `SecurityConfig`, правила вроде «это ваш предмет» стоят на методах контроллеров в `@PreAuthorize`.

## База данных

- `db/1_schema.sql`: таблицы и ограничения, включая `user_sessions` (сессии удаляются вместе с пользователем).
- `db/2_seed.sql`: тестовые данные.
- `db/3_grants.sql`: права сервисной роли на `user_sessions`: чтение, добавление и изменение строк.

## Как запустить

Нужны Java 17, Maven и MySQL 8.

1. В пустой базе по очереди выполняю `db/1_schema.sql`, `db/2_seed.sql`, `db/3_grants.sql`.
2. В корне проекта создаю файл `.env` (он не попадает в git):

   ```
   DB_URL=jdbc:mysql://хост:3306/имя_базы?characterEncoding=UTF-8
   DB_USER=пользователь
   DB_PASSWORD=пароль
   JWT_SECRET=секрет_в_Base64
   ```

3. Запускаю приложение:

   ```bash
   mvn spring-boot:run
   ```

## Коллекция запросов

Файл `postman_collection.json`. В Postman: **Import**, выбираю файл, запускаю приложение, у коллекции нажимаю
**Run** и **Run collection**. Внутри 90 запросов с проверками. Папка «2. Access и refresh» повторяет сценарий
задания на пользователе `ivan`:

1. `POST /auth/login`: получить пару, в базе появляется запись `ACTIVE`.
2. С access открыть защищённый endpoint.
3. `POST /auth/refresh`: получить новую пару, строки токенов отличаются. Первая запись `USED`, новая `ACTIVE`.
4. Повторно отправить старый refresh: `401`, новой пары нет.
5. В базе первая запись `REVOKED`, вторая `ACTIVE`, лишней записи нет. Проверяю запросом:

   ```sql
   SELECT id, device_id, status, access_token_expiry, refresh_token_expiry
   FROM user_sessions WHERE username = 'ivan' ORDER BY access_token_expiry;
   ```

Остальные папки проверяют регистрацию, ошибочные токены, права по ролям, бизнес-операции, блокировку
пользователя и защиту от подбора пароля. Созданные пользователи в конце удаляются вместе с их сессиями.
