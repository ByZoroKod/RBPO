# Аукцион коллекционных предметов: аутентификация и авторизация

Это REST API для аукциона. Пользователь выставляет свой коллекционный предмет на торги, другие делают ставки,
а когда торги заканчиваются, победитель получает предмет. Написано на Java 17 и Spring Boot, данные хранятся
в MySQL.

В этом задании я добавил Spring Security: вход по логину и паролю, регистрацию, роли, защиту от CSRF и проверку
прав. CRUD и пять бизнес-операций остались такими же, как в прошлом задании, но теперь доступны не всем.

## Сущности

| Что | Адрес |
|---|---|
| Пользователь (имя, e-mail, логин, хэш пароля, роль, статус) | `/api/users` |
| Коллекционный предмет | `/api/collectible-items` |
| Аукционный лот | `/api/auction-lots` |
| Ставка | `/api/bids` |
| Сделка (теперь с продавцом) | `/api/auction-deals` |
| Регистрация и CSRF-токен | `/api/auth` |

## Как устроена безопасность

- **Вход.** HTTP Basic: логин и пароль идут в заголовке `Authorization` каждого запроса. Сессий нет. Пароли
  в базе хранятся только как хэш BCrypt (`PasswordEncoder`).
- **CSRF.** Запросы `POST`, `PATCH`, `DELETE` требуют токен. Его получают через `GET /api/auth/csrf` (токен
  приходит в ответе и в cookie `XSRF-TOKEN`) и передают в заголовке `X-XSRF-TOKEN`. Без токена будет `403`.
- **Регистрация.** `POST /api/auth/register`. Логин: 3–50 символов (латиница, цифры, `_`, `.`, `-`), уникальный.
  Пароль: не короче 8 символов, с заглавной и строчной буквой и цифрой, без логина внутри. Роль всегда `USER`,
  поле `role` из запроса игнорируется.
- **Статус.** У пользователя статус `ACTIVE` или `BLOCKED`. Заблокированный войти не может. Блокирует администратор.
- **Подбор пароля.** После 5 неверных паролей подряд вход для этого логина закрывается на 15 минут.

## Роли и права

Ролей две: `USER` (участник торгов) и `ADMIN` (модератор).

| Операция | USER | ADMIN |
|---|---|---|
| Смотреть предметы, лоты, ставки | да | да |
| Профиль пользователя | только свой, менять имя, e-mail, пароль | любой, плюс роль и статус |
| Список пользователей, создать и удалить пользователя | нет | да |
| Создать предмет | только на себя | на любого |
| Изменить или удалить предмет | только свой и не во время торгов | любой |
| Выставить предмет на торги | только свой | только свой |
| Сделать ставку | да, от своего имени | нет |
| Завершить торги | только по своему лоту | любые |
| Подтвердить передачу | только продавец | любую |
| Отменить сделку | продавец или победитель | любую |
| Смотреть сделку | продавец или победитель | любую |
| Создать, изменить, удалить лот, ставку, сделку напрямую | нет | да |

Кто делает ставку, берётся из логина, а не из тела запроса. Владельца предмета обычный пользователь тоже
изменить не может: поле `ownerId` игнорируется. Общие правила по адресам и ролям описаны в `SecurityFilterChain`
(`SecurityConfig`), а правила вроде «это ваш предмет» стоят на методах контроллеров в `@PreAuthorize`.

## Ошибки

| Код | Когда |
|---|---|
| `401` | не пройдена аутентификация: нет логина, неверный пароль, пользователь не найден или заблокирован |
| `403` | нет прав или нет CSRF-токена |
| `400` | неправильные данные: слабый пароль, плохой логин, сломанный JSON |
| `404` | не найдено |
| `409` | нарушено правило бизнеса или ограничение базы (владелец ставит на свой предмет, логин занят) |

Ответ всегда в одном виде: `status`, `message`, `timestamp`. Для неверного пароля, несуществующего логина и
заблокированного пользователя сообщение одинаковое, хэши паролей и технические подробности в ответы не попадают.

## База данных

Таблицы, связи и ограничения описаны в `db/1_schema.sql`: связанные записи удаляются каскадом, цены больше нуля,
логин и e-mail не повторяются, один предмет нельзя выставить на двое торгов сразу, по лоту не больше одной сделки.

## Бизнес-операции

Те же, что в прошлом задании, теперь с проверкой прав:

- `POST /api/collectible-items/{id}/list-for-auction`: выставить предмет на торги;
- `POST /api/auction-lots/{id}/place-bid`: сделать ставку, тело `{"amount": 1000}`;
- `POST /api/auction-lots/{id}/close`: завершить торги;
- `POST /api/auction-deals/{id}/confirm-transfer`: подтвердить передачу;
- `POST /api/auction-deals/{id}/cancel`: отменить сделку.

## Как запустить

Нужны Java 17, Maven и MySQL 8. Базу и пользователя для неё создаю заранее. Таблицы приложение само не создаёт.

1. В пустой базе один раз выполняю `db/1_schema.sql`, затем `db/2_seed.sql` (тестовые данные).
2. В корне проекта создаю файл `.env` (он не попадает в git):

   ```
   DB_URL=jdbc:mysql://хост:3306/имя_базы?characterEncoding=UTF-8
   DB_USER=пользователь
   DB_PASSWORD=пароль
   ```

3. Запускаю приложение:

   ```bash
   mvn spring-boot:run
   ```

## Коллекция запросов

Файл `postman_collection.json`. В Postman: **Import**, выбираю файл, запускаю приложение, у коллекции нажимаю
**Run** и **Run collection**. Внутри 70 запросов с проверками: CSRF-токен, регистрация, вход, права по ролям,
все бизнес-операции, действия администратора, блокировка после неверных паролей. Токен и id запоминаются сами,
созданные пользователи в конце удаляются, так что коллекцию можно запускать несколько раз.
